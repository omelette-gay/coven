# Keycloak Client

Creates an OpenID Connect client to allow an app to integrate with Keycloak, and writes what the app needs to use it
into a Kubernetes Secret. See [single sign-on](../../docs/sso.md) for what to check before putting an app behind SSO.

## The Secret

Every client's Secret has the same keys, so apps can be pointed at any of them:

| Key | Value |
|---|---|
| `client_id` | The client's ID |
| `client_secret` | The client's secret |
| `authorization_endpoint` | `<keycloak_url>/realms/<realm>/protocol/openid-connect/auth` |
| `token_endpoint` | `.../token` |
| `userinfo_endpoint` | `.../userinfo` |
| `jwks_endpoint` | `.../certs` |

An app that discovers the endpoints itself (from `.well-known/openid-configuration`) can ignore the last four.

## Rotating the client secret

The client secret is generated by Terraform each time it runs, but only written, to both Keycloak and the Kubernetes
Secret, when `secret_revision` changes. It starts at 1 and the module otherwise never touches the secret again. So
increase `secret_revision` (by one) to:

- **Rotate the client secret**, for example if it may have leaked, or if someone who could read it has left. The new
  secret is written to Keycloak and the Kubernetes Secret in the same apply.
- **Give a client the standard keys.** A client created before the endpoints were added keeps its old Secret (just
  `client_id` and `client_secret`) until the revision is increased. GlitchTip is one of these.
- **Put the Secret back as Terraform would write it**, if its contents were changed by hand. (If the Secret is deleted,
  Terraform recreates it on the next apply without a change to the revision.)

It always rotates the secret and rewrites every key together, so there's no way to do one without the other. Rotating
breaks SSO until the app has the new secret, so, before increasing it:

- Apps read the Secret when they start, so restart them (or deploy them) afterwards.
- If the app keeps its own copy of the secret, update that too. GlitchTip does: its `configure_oidc` Job writes the
  secret into GlitchTip's own database, so rotate it with `keycloak_secret_revision` in the GlitchTip module, which
  re-runs the Job.

## State

The client's secret ends up in Terraform state, and so does the Secret's contents. Setting them with write-only
arguments only keeps the values in our configuration out of state: the Keycloak provider reads `client_secret` back
after writing it, and the Kubernetes provider does the same with a Secret's `data`. The first can't be avoided, and as it's
the same value, writing the Secret through Vault instead wouldn't help. See
[secrets and Terraform state](../../docs/secrets.md#secrets-and-terraform-state).

## Granting roles

`role_groups` grants client roles to groups that already exist, as a map of role to group names. The module doesn't
create groups or manage who's in them, and it only adds the grants: other roles the group holds, from this client or
any other, are left alone.
